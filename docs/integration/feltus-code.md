# FELTUS CODE integration

FELTUS CODE is served from the core application at `/api/code/ui` and its same-origin assets. It does not introduce another authentication provider, API gateway, AI runtime, or deployment stack. The primary FELTUS `CODE` navigation opens the project workspace in a same-origin frame.

## Project isolation and storage

Each repository root is computed on the server as `FELTUS_CODE_WORKSPACE_ROOT/<authorized FELTUS application UUID>`. Browser requests carry an application ID, but never a filesystem path. The server resolves the application using the current authenticated FELTUS access token and Postgres RLS; file, Git, AI, and task writes also require project write access. The source rejects symlink traversal and parent-repository inheritance: Git operations require a direct `.git` entry and an exact `git rev-parse --show-toplevel` match. The current Windows test host skipped symlink/junction runtime cases when it denied link creation; this is source-level coverage only for that host, as recorded in the go-live status. It also strips ambient `GIT_*` overrides and disables system/global Git config so a host-level Git setting cannot redirect repository operations or inject hooks into workspace initialization.

In local development, `scripts/dev.js` places workspaces under `.feltus-storage/code-workspaces` and approves only folders under `development/test-fixtures` for the `seed_local` workspace action. The action takes a single child-folder name, copies safe regular files into a temporary private workspace, initializes Git there, and atomically installs it under the authorized app UUID. It excludes secrets, Git metadata, dependencies, builds, caches, and runtime-only files; it never exposes the source folder to Preview. Repeating the same seed does not replace workspace edits. Production does not configure or expose this action. Production Compose mounts the persistent `feltus_code_workspaces` volume at `/data/feltus-code`; the Docker image prepares that path for its non-root `node` user. `scripts/backup.sh` includes this volume's repository data in the private storage archive, and `scripts/restore-storage.sh` restores it into a separate recovery Compose project. Keep this volume in the same backup and restore cycle as the FELTUS database.

## Database records

Apply `supabase/migrations/20261102010000_feltus_code.sql` through the existing migration runner. It adds one active session per project, action/usage records, and explicit Git checkpoint records. All tables enable RLS and use `feltus_can_access_app`; anonymous access is revoked. Authenticated clients can update only the session's `updated_at` and `model` columns.

## AI and tasks

Model choices come from `/api/ai/models`. Plans stream through `/api/code/ai/plan/stream` when the configured FELTUS provider exposes a stream API; cancellation propagates to the provider and task runner. Every AI action requires a selected file. The browser sends only its project-relative path; the server reads current contents from that authorized project's workspace, rejects traversal and symlinks, and supplies the verified source as grounding context. Unsaved editor changes must be saved before requesting AI. Secret-like source remains excluded, and edit proposals include source hashes so a stale proposal cannot overwrite newer work. Applying an edit requires an explicit user action. Agent mode requires confirmation, limits edits to selected files, and runs one of the server's actual repository validation tasks; it has no arbitrary shell tool.

Agent validation runs in a temporary workspace containing the current project state plus the proposed file contents. The original workspace is changed only after the selected validation task exits successfully. A failed or unavailable task leaves the proposal unapplied and is reported with its reason; a proposal path can be applied at most once. Validation choices are detected from the workspace: npm tasks require a matching `package.json` script, while initialized simple repositories retain `git-status` and `git-diff`. The UI shows unavailable tasks with their reason and defaults to an available check.

AI project-source context is sent only when the existing AI endpoint trust policy allows `FELTUS_AI_SEND_PROJECT_CONTEXT`. That default remains false for production configuration. Conversation history is not appended to FELTUS CODE requests. Keep `FELTUS_AI_SEND_HISTORY=false` until the runtime has been verified as trusted/private.

## Current UI boundary

The first integrated editor is an accessible, line-numbered plain-text editor with tabs, dirty state, optimistic SHA-256 writes, and reviewable proposal output. It has no third-party CDN dependencies. Monaco and language-specific syntax highlighting are not included in this release; the editor surface is isolated in `src/feltus-code/web/index.html` and its stylesheet/script so it can be replaced without changing the server API.

FELTUS CODE can initialize a new empty private repository per application, or seed a preapproved local development fixture through the existing authenticated workspace route. It does not clone a remote repository, push, merge, deploy, or read another workspace. Those actions remain outside this integration.

The standalone scaffold's mock `dev-server.mjs`, nested package manifest, and scaffold migration are retained for local reference but excluded from the production Docker build context. Production CODE UI/API routes use only the core FELTUS server and its configured AI Gateway.

## Repository finalization and Day-2 lifecycle

**Complexity absorption principle:** “FELTUS absorbs implementation complexity by default. Users interact with intent, outcomes, exceptions, and material decisions. Technical implementation evidence remains available through progressive disclosure.”

**Productionization principle:** “Generated applications are finalized through stack-aware repository productionization and validation so that released source conforms to conventional engineering practices for its actual language and framework while preserving application behavior and protected contracts.”

Implementation status:

- **Implemented in the local CODE flow:** Repository evidence is classified for language roles, frameworks, runtime/version evidence, package managers and per-ecosystem conflicts, build tools, formatters, linters, type checkers, configured test runners and locations, database clients, migrations, container/infrastructure files, and provider configuration. Every inferred framework includes evidence paths. The standard resolver reports `SATISFIED`, `PARTIAL`, `MISSING`, `NOT_APPLICABLE`, or `UNKNOWN` and keeps repository configuration separate from recommended tools.
- **Source binding:** CODE resolves the authorized workspace server-side, records its application/workspace identity, Git branch, commit/checkpoint, and a deterministic SHA-256 of the inspected snapshot. Classification and the contract map share the same snapshot object. The Git head and working-tree status are checked around the scan; an unstable or dirty workspace cannot pass the clean-checkpoint release gate. Classification is recomputed for each overview/validation request, so a changed snapshot is not served from a stale cache. An explicitly requested checkpoint that differs from the current head is rejected.
- **Bounded evidence:** The scanner skips `.git`, dependency/build/cache directories, symlinks, and sensitive paths; reads small UTF-8 evidence files only within per-file and total limits; hashes other regular files within a total byte budget; and never returns file contents or environment-variable values. If a source evidence file, file-count limit, or hashing limit prevents complete inspection, the result is marked incomplete and required release checks are unavailable. Binary files are hashed but not parsed as source.
- **Protected contracts:** The map separates low-risk internal files, medium-risk manifests/tests, and contract-protected routes, schema/migration/generated/type/SDK/webhook paths, database identifiers, RPCs, enums, serialized state fields, provider events, FELTUS application-state markers, and environment-variable references. Environment-variable names are extracted only from code references; arbitrary uppercase strings are not treated as names. Contract detection remains a conservative heuristic and is not a proof of behavioral equivalence.
- **Partially implemented:** Safe JSON formatting can be proposed deterministically; other normalization is a reviewable CODE change set. The built-in normalizer does not yet run native formatter fixes or language AST rewrites, and contract detection is heuristic. A protected-path classification is a conservative review signal, not a proof of behavioral equivalence or a substitute for security analysis.
- **Implemented locally, not runtime verified:** Finalization runs the detected required checks in an isolated temporary workspace. Failed or unavailable required checks block release readiness while a proposed change can still be reviewed. A clean, explicitly saved source checkpoint and matching validation evidence are required before build, deployment, or promotion requests can pass the release gate.
- **Implemented through existing records:** Productionization run IDs, check results, source snapshots, transformations, apply actions, and checkpoint commits are correlated in CODE activity. Existing usage records continue to record AI usage. Retrieved document/chunk identifiers and a context fingerprint are not yet recorded for every execution path; complete provenance remains partial.
- **Partially implemented for Day 2:** The owner can validate an observed source checkpoint and accept an unpersisted desired state as a new immutable Blueprint. Restoring a version requires an explicit Blueprint, environment, reason, and authorized user, and queues the existing deployment rollback RPC. Current observations remain deployment-level; richer runtime-configuration, schema, and infrastructure-target observations are not claimed.
- **Implemented locally, not runtime verified:** Export reads a recorded Git checkpoint and produces a portable tar archive with source, applicable database and infrastructure assets, a manifest, dependency/build metadata, and environment variable names. Sensitive paths and detected secret values are excluded or redacted. The archive preserves the exact commit as its source, subject to that secret filtering. No live provider is contacted by export or local validation.

The `feltus.application-state/v1` identity and hash algorithm are unchanged. Source commit remains part of desired-state identity. Local checkpoint commits are reconstructed into the existing `desired_state.code.commit` field and therefore follow the existing v1 hash behavior; previously saved Blueprints are not rewritten. No new productionization database table or RLS policy is introduced.

### Phase F productionization pipeline

The local CODE pipeline consumes Phase E's source-bound classification, engineering standard, test locations, and protected-contract map. A plan rechecks the application/workspace identity, branch, committed checkpoint, complete source snapshot hash, and classifier version before recording a run. It executes available baseline checks in an isolated workspace, proposes only bounded JSON formatting changes that preserve parsed values, and creates a reviewable change set tied to that exact source identity. Secret-bearing and protected files are excluded.

Candidate validation uses the same isolated CODE task runner and adds a deterministic JSON semantic check. A failed or unavailable required check blocks application and release readiness while retaining the review result. Low-risk proposals still require review and explicit application. Medium-risk manifest and test changes require an explicit, exact-path review confirmation. Protected contract changes are blocked until handled through a versioned compatibility or migration workflow. Application, stage, and checkpoint operations require the recorded run, validation evidence, unchanged source snapshot, and exact proposed path set; undo remains available through CODE's existing change-set backup flow. No push, deployment, provider call, database migration, or RLS policy change is part of this pipeline.

The classifier groups JavaScript and TypeScript as one source ecosystem while treating SQL and shell files as supporting assets. Unknown, incomplete, conflicting, or mixed primary-language stacks remain blocked from stack-specific automation. Deterministic normalization is currently limited to semantic-preserving JSON formatting; the system does not rewrite arbitrary source, change dependencies, or select new frameworks. Candidate recommendations remain reviewable evidence, not proof of behavioral equivalence.

Automated coverage exercises JavaScript and TypeScript proposals through validation and CODE lifecycle gates, Python test and syntax checks, static-site classification, protected/medium-risk review, stale-plan rejection, secret exclusion, and unknown/mixed blocking. Go detection is covered; its native check blocks when the Go toolchain is unavailable. The actual FELTUS root remains a dirty, mixed-language negative acceptance case and is not a productionization target.

These are source and automated-test claims only. Authenticated browser flows, a clean-checkout run, production databases, and provider-side deployment behavior have not been verified.

### Phase F.5 Design Studio

Design Studio is a first-class pane inside the existing CODE workspace. It uses the existing application Intelligence and capability graph to recommend 75 structured recipes, while a single feltus.design-state/v1 record carries tokens, responsive rules, page settings, Brand Guardrails, and per-component ownership and synchronization. Setup-data storage uses a reversible, versioned field-key encoding for names rejected by the existing secret-key validator; application-state reconstruction decodes it before constructing the canonical application blueprint.

The Canvas supports a bounded set of marked HTML component identities and writes generated conventional CSS through the same CODE proposal, contract review, isolated validation, exact-path staging, checkpoint, and undo flow. Preview loads the actual isolated app Preview. AI receives selected scope and a bounded redacted managed-component excerpt, and returns structured property actions only. It cannot write arbitrary source.

Reconciliation is component-scoped for supported external variant edits and supported structural recovery. Unsupported changes preserve the external source and make only the affected component Developer Managed. A developer stylesheet edit is tracked separately and blocks visual proposals rather than being overwritten. Arbitrary source-to-Canvas reversibility is not claimed.

The disposable acceptance fixture is exercised by npm run test:design-studio. It tests persistent state encoding, recommendation, recipe and component changes, responsive isolation, AI scoping, Brand Guardrails, stale-source and protected-contract blocking, component-scoped reconciliation, reconnect, Preview source delivery, isolated CODE validation, and checkpoint/undo. A real authenticated browser workflow and live model/provider execution remain outside this fixture's verification boundary.

### Phase G Release Readiness

Release Readiness extends the existing CODE lifecycle; it does not create a build, deployment, or provider subsystem. `POST /api/code/release-readiness/evaluations` evaluates the exact authorized application source and writes its terminal evidence through the existing CODE activity stream. `GET /api/code/release-readiness` and `GET /api/code/release-readiness/evaluations/:id` resolve stored evidence against current source, configuration, and Design Studio bindings and return `STALE` rather than silently treating prior evidence as authoritative.

The bounded release states are `READY`, `NOT_READY`, `REVIEW_REQUIRED`, `VALIDATING`, `STALE`, and `BLOCKED`. Every evaluation binds application, workspace, branch, checkpoint/commit, complete source snapshot hash, classifier version, productionization validation state, Design State/reconciliation state when applicable, and declared configuration/environment metadata. Categories are Code, Tests, Design, Configuration, Security, Build, and Environment; each detailed check is a `BLOCKING`, `REVIEW REQUIRED`, `WARNING`, or `NOT APPLICABLE` gate with source identity, timestamp, expected/observed state, evidence references, and remediation.

The CODE panel presents the release answer first, category summaries second, and detailed technical evidence only when expanded. Existing Design Studio behavior is preserved: a synchronized Developer Managed component does not block release on ownership alone, reconciliation work is review-required unless it is unsafe, and source/design or managed-stylesheet conflicts remain blocking. `READY` may make only the exact source build-eligible. The existing build action must still be explicitly invoked and rechecks current readiness; evaluation itself never creates a build, artifact, deployment, promotion, or provider call. Environment evidence is metadata-only and never contacts a deployment provider or reveals secret values.

Build, deployment, and promotion gates perform a read-only GitHub branch lookup for a connected repository and require the remote branch commit to match the selected source commit. The resulting `REMOTE_VERIFIED`, `REMOTE_DIVERGED`, or `REMOTE_UNAVAILABLE` status accompanies the action response; `NOT_CONNECTED` is used when no external repository participates. `GET /api/apps/:appId/lineage` does not contact GitHub by default; pass `verify_remote=true` for an explicit current remote check, otherwise a connected source is marked `NOT_CHECKED`.
